# 한국어 업무 글쓰기 평가 후보: 기술 문서·서비스 상태·데이터 주장

조사일: 2026-09-14. 이 문서는 공개된 1차 자료를 실제로 읽고 도출한 **평가 후보**다. 토스페이먼츠 한국어 개발 문서, Google Cloud 한국어 제품 설명, Google Drive 한국어 도움말을 중심으로 하며, 통계 개념은 Eurostat와 호주 통계청(ABS), 기술 문서 작성 원칙은 Google의 영문 지침으로 보완했다.

## 해석 원칙

- **출처가 입증하는 것:** API 필드·상태·제약의 실제 의미, 통계 개념, 해당 제공자의 문서 작성 지침.
- **출처가 입증하지 않는 것:** 한국 직장인의 오류 발생률, 이 저장소의 글쓰기 도구가 특정 오류를 일으킨다는 사실, 아래 상황의 실제 발생 여부. 빈도 조사는 하지 않았다.
- 아래 14개 입력은 모두 **[추론·합성]**이다. 실제 고객 데이터·사내 대화·개인 문서가 아니다. 제품 계약의 경계를 압축하거나 문장을 매끈하게 만드는 과정에서 의미가 바뀔 가능성을 연구자가 구성했다.
- API 전문지식 퀴즈가 되지 않도록 평가 입력에 필요한 계약·범례·기준시점을 함께 제공한다. 문장 하나의 정답을 고정하기보다 토큰, 상태, 수치, 조건, 근거 수준이 보존되는지 관찰한다.
- 편집 범위가 ‘맞춤법만’이라면 숫자나 사실을 묵묵히 바꾸지 말고 별도 확인 사항으로 알리는 방식도 허용한다. 반대로 ‘사실관계도 검토’라면 입력 안의 근거로 확인되는 오류를 그대로 매끈하게 포장하는 것은 실패다.
- 영문 스타일 가이드의 공백·대문자·링크 문구를 한국어의 보편적인 강제 규정으로 이식하지 않는다. 여기서는 의미 손실을 막는 원칙만 차용한다.

## 1. 실제 확인한 출처와 적용 범위

### S1. 토스페이먼츠 — 코어 API

- URL: https://docs.tosspayments.com/reference
- 실제 읽은 부분: `결제 → Payment 객체 → 객체 상세`의 `status`, `totalAmount`, `balanceAmount`, `approvedAt`, `taxFreeAmount`, `card.installmentPlanMonths`, `virtualAccount.refundStatus`, `refundReceiveAccount`, `cashReceipt.receiptUrl`, `cashReceipts` 설명. 전체 API를 읽었다는 뜻은 아니다.
- 확인된 계약:
  - `IN_PROGRESS`는 결제수단 인증을 마친 상태이고 승인 API 호출로 결제가 완료된다. `WAITING_FOR_DEPOSIT`는 가상계좌 입금 전 상태, `DONE`은 결제 승인 상태다.
  - 가상계좌 `refundStatus`의 `PENDING`은 환불 처리 중, `COMPLETED`는 환불 완료다. 결제 승인과 환불·정산은 서로 다른 상태 축이다.
  - `totalAmount`는 취소 후에도 최초 결제 금액을 유지하고, `balanceAmount`는 취소 후 남은 취소 가능 금액이다.
  - `approvedAt`은 nullable이다. `taxFreeAmount`의 `0`은 일반 상점의 면세 금액 응답값이고, `installmentPlanMonths`의 `0`은 일시불이다.
  - `refundReceiveAccount`는 결제창을 띄운 시점부터 30분 동안만 조회할 수 있고 이후 값이 내려가지 않는다.
  - 테스트 환경의 현금영수증 URL은 생성되지만 실제 데이터는 제공되지 않는다. 결제 승인 후 별도 발급 API로 발급한 현금영수증은 기존 결제 정보에 연결되지 않아 `cashReceipts`가 `null`일 수 있으며 별도 조회 API를 안내한다.
- 적용 경계: 토스페이먼츠의 해당 필드·버전 계약이다. 모든 시스템의 `0`, `null`, 누락이 같은 뜻이라는 일반 규칙으로 확대하면 안 된다. 상태 문자열만 보고 그 문자열이 속한 필드를 생략해서도 안 된다.

### S2. 토스페이먼츠 — 인증 및 기타 헤더 설정

- URL: https://docs.tosspayments.com/reference/using-api/authorization
- 실제 읽은 부분: `멱등키 헤더 → 멱등키 사용하기`, `에러 처리하기`, `선택 요청 헤더 → 테스트 환경에서 에러 재현하기`.
- 확인된 계약:
  - `Idempotency-Key`를 사용해 같은 요청을 재전송할 수 있다. 키는 최초 요청일로부터 15일간 유효하다.
  - 동일 요청 판정에는 멱등키뿐 아니라 API 키, API 주소, HTTP 메서드 조합이 쓰인다.
  - 멱등 요청에서 오류가 반환됐다고 키를 바꿔 같은 요청을 재시도하는 것은 위험하며 원인을 확인하라고 명시한다.
  - 첫 요청 처리 중 같은 요청을 보내면 HTTP `409`와 `IDEMPOTENT_REQUEST_PROCESSING`이 돌아올 수 있다. 문서는 다시 요청하여 응답을 확인하도록 안내한다.
  - 모든 POST API에 멱등키 헤더를 사용할 수 있고, GET의 멱등키 헤더는 무시된다.
  - `TossPayments-Test-Code`는 테스트 API 키와 쓰며 라이브 환경에서는 무시된다.
- 적용 경계: 모든 HTTP `409`를 같은 처리 중 상태로 해석할 수 없다. ‘재시도’ 자체를 항상 금지하는 규칙도 아니다. 새 업무 요청, 유효기간, 제공자별 계약을 구분해야 한다. 이 자료만으로 재시도 간격·횟수·영구적 중복 방지를 만들어낼 수 없다.

### S3. 토스페이먼츠 — 요청·응답 본문

- URL: https://docs.tosspayments.com/reference/using-api/req-res
- 실제 읽은 부분: `응답 HTTP 상태 코드`, `에러 객체 → API v1 에러 객체 / API v2 에러 객체`, `유의사항`.
- 확인된 계약: HTTP 상태 코드와 응답 객체의 에러 `code`, `message`는 다른 항목이다. v1 예시는 `NOT_FOUND_PAYMENT` 코드와 한국어 메시지를 포함한다. v2는 `traceId` 및 중첩된 `error` 객체를 설명한다. 새 응답 필드는 버전 릴리즈 없이 추가될 수 있다.
- 적용 경계: 해당 API의 상태 코드 설명을 다른 제공자의 API에 적용하지 않는다. 원시 응답 인용과 사용자에게 보여 줄 설명 문구는 서로 다르다.

### S4. 토스페이먼츠 — API 버전 정책

- URL: https://docs.tosspayments.com/reference/versioning
- 실제 읽은 부분: 서두, `버전 릴리즈 정책`의 두 하위 절, `내 상점의 API 버전 확인·변경하기`.
- 확인된 계약: 새 버전이 나와도 기존 상점 버전을 자동 변경하지 않는다. 새 응답 필드·새 ENUM·에러 메시지 변경은 새 버전 없이 반영할 수 있지만 엔드포인트 제거·필드 삭제·같은 의미의 에러 코드 변경은 새 버전 릴리즈 사유다. 테스트 환경과 라이브 환경의 버전은 다를 수 있다. 이 정책은 2022-06-08 버전부터 적용한다고 명시한다.
- 적용 경계: 문서의 최신 버전, 테스트에서 확인한 버전, 실제 운영 버전을 동일시하지 않는다. 이 정책이 모든 제공자의 버저닝 원칙을 대표하지는 않는다.

### S5. Google — Code in text

- URL: https://developers.google.com/style/code-in-text
- 실제 읽은 부분: 서두, `Some specific items to put in code font`, `Items to put in ordinary (non-code) font`, `Items that are sometimes in code font`, `HTTP status codes`, `Grammatical treatment of code elements`.
- 확인된 지침: 코드 서식은 그대로 입력할 문자열과 경계를 표시한다. 속성명·값·명령 출력·자료형·HTTP 상태 코드·메서드 등을 구분한다. 제품명·일반 개념·브라우저 탐색용 URL을 모두 코드처럼 취급할 필요는 없다.
- 적용 경계: 영어 문서의 스타일 지침이다. 한국어 조사를 붙이는 방식, 백틱 사용 여부 자체를 단일 정답으로 삼지 않는다. 식별자 내부의 철자·대소문자·구두점을 임의로 교정하지 않는 것이 핵심이다.

### S6. Google — Units of measurement

- URL: https://developers.google.com/style/units-of-measure
- 실제 읽은 부분: `Currency`, `Rates`, `Decimal and binary units`, `Ranges of numbers with units`.
- 확인된 지침: 문서화하는 기술과 같은 단위 체계를 써야 하며 MB/MiB, GB/GiB를 혼동하지 않는다. 달러 기호만으로 통화가 모호하면 통화 표시를 추가한다. 범위의 단위와 의미가 분명해야 한다.
- 적용 경계: 영어의 `per`나 숫자·단위 공백 지침을 한국어에 강제하지 않는다. API 설정값·로그값의 단위는 해당 계약이 우선이다. 데이터량과 전송률도 별개다.

### S7. Eurostat — Glossary:Percentage point / Percentage change

- URL: https://ec.europa.eu/eurostat/statistics-explained/index.php?title=Glossary:Percentage_point
- URL: https://ec.europa.eu/eurostat/statistics-explained/index.php?title=Glossary:Percentage_change
- 실제 읽은 부분: 두 페이지의 본문 정의와 계산식 전체.
- 확인된 정의: 두 백분율의 차이는 퍼센트포인트로 표현한다. 10%에서 12%는 2 percentage points 증가다. 상대 변화율은 `(나중 값 / 이전 값 - 1) × 100`이다.
- 적용 경계: 공식 통계 개념이지 특정 회사 KPI의 분모·집계 대상을 보증하는 자료는 아니다. 이전 값이 0일 때 해당 상대 변화율 공식을 그대로 사용할 수 없다는 점은 수학적 추론이다. `pp`를 한국어에서 반드시 써야 한다는 의미는 아니다.

### S8. Australian Bureau of Statistics — Correlation and causation

- URL: https://www.abs.gov.au/statistics/understanding-statistics/statistical-terms-and-concepts/correlation-and-causation
- 실제 읽은 부분: `The difference between correlation and causation`, `Importance of correlation and causation`, `Measuring correlation`, `Establishing causation`.
- 확인된 설명: 상관관계가 있다고 원인·결과가 자동으로 성립하지 않는다. 다른 요인 때문에 두 변수가 함께 변할 수 있다. 상관계수는 보통 선형 관계를 측정하므로 비선형 관계에서 0에 가까울 수 있다. 통제된 연구가 인과관계 확립에 효과적이며 관찰연구는 다른 정보와 함께 근거를 제공한다.
- 적용 경계: ‘인과 표현은 언제나 금지’라는 규칙이 아니다. 적절한 연구 설계와 추가 근거가 있으면 인과 주장을 검토할 수 있다. 본문 앞부분의 `r=0`에 대한 간단한 설명만 떼어 쓰지 않고 뒤의 선형성 한계까지 함께 읽었다.

### S9. Google Cloud — 제품 및 서비스: 제품 출시 단계

- URL: https://cloud.google.com/products?hl=ko#product-launch-stages
- 대조한 영문 URL: https://cloud.google.com/products#product-launch-stages
- 실제 읽은 부분: `프리뷰 / Preview`, `정식 버전 / General Availability`, `지원 중단됨 / Deprecated`.
- 확인된 설명: 프리뷰는 기능이 완성되지 않았을 수 있고 SLA 또는 기술 지원 약정이 제공되지 않으며 Google이 달리 명시하지 않으면 테스트 환경용이다. 정식 버전은 프로덕션 사용에 적합하고 **해당하는 경우** SLA가 적용된다. 한국어의 ‘지원 중단됨’은 여기서 **서비스 종료 및 삭제가 예정된 기능**이며 영문 `Deprecated`에 대응한다.
- 적용 경계: 출시 단계의 일반 설명이지 특정 제품의 종료일·개별 계약 확인이 아니다. `Deprecated`를 곧바로 ‘이미 삭제됨’으로 바꾸거나 반대로 영구 지원으로 해석할 수 없다. 특정 제품의 별도 조건이 있으면 이를 우선 확인한다.

### S10. Google — Cross-references and linking

- URL: https://developers.google.com/style/cross-references
- 실제 읽은 부분: `Choose links selectively`, `Write descriptive link text`, `Avoid vague link text`, `Avoid URLs as link text`, `Explain unexpected link behavior`, `Open links in the current tab`.
- 확인된 지침: 설명적인 링크 이름은 스크린리더 이용자와 훑어 읽는 독자에게 도움이 된다. 링크만 보고 목적이 드러나야 하며 PDF 다운로드 등 예상 밖 동작을 알린다. 짧은 필수 맥락은 본문에 제공할 수 있다. 일부 법률 문서는 URL 자체를 링크 문구로 쓰는 예외가 있다.
- 적용 경계: 링크 이름이 좋다고 접근 권한이나 대상 문서의 진실성이 검증되지는 않는다. 메신저의 원시 URL, 감사 추적, 법률 서식 등에서는 URL을 그대로 남길 이유가 있다.

### S11. Google Drive — Google Drive에서 파일 공유하기

- URL: https://support.google.com/drive/answer/2494822?hl=ko
- 실제 읽은 부분: `공유 권한 이해하기`, `특정 대상과 공유하기 → 특정 사용자와 공유하기`, `공개 공유 및 공동작업에 대해 자세히 알아보기`, `공유 파일 관리하기 → 파일의 일반 액세스 권한 변경하기`.
- 확인된 설명: 뷰어·댓글 작성자·편집자 권한은 다르다. 직장·학교 계정은 외부 공유가 제한될 수 있다. ‘제한됨’은 권한이 있는 사용자만 열 수 있고, ‘링크가 있는 모든 사용자’는 링크를 가진 사용자가 로그인 없이 사용할 수 있다.
- 적용 경계: 공개 도움말을 읽었다고 실제 사용자의 문서 권한이나 내용을 확인한 것은 아니다. 메일에 링크를 붙이는 행위와 상대방이 문서를 읽을 수 있는 상태는 다르다. 실제 권한 변경은 이 연구의 범위가 아니다.

## 2. 합성 평가 후보 14개

아래의 합격 조건은 의미 기준이며 정해진 문구를 요구하지 않는다. 각 사례는 단독으로 실행할 수 있도록 필요한 사실을 입력에 포함했다.

### T01. 원시 오류 토큰과 설명 문장의 경계

- **[추론·합성 입력]** “개발팀 장애 공유를 다듬어 줘. 로그 원문은 그대로 둬. `HTTP 409`, `code=IDEMPOTENT_REQUEST_PROCESSING`, `message=이전 멱등 요청이 처리중입니다.`가 찍혔어. 앞서 보낸 요청이 처리 중이라는 뜻이야. 결제 실패가 확정된 것은 아니야.”
- 근거: S2의 에러 처리, S3의 에러 객체, S5의 코드 서식.
- 예상 편집 실패: 영문 토큰을 번역·소문자화하거나 원시 메시지의 띄어쓰기를 조용히 바꿈. ‘오류’라는 말만 남겨 결제 실패로 단정함.

- 정당한 예외: 문서가 애초에 테스트 범위만 다루며 제목·맥락에 그 범위가 명확하면 문장마다 ‘테스트’를 반복할 필요는 없다. 새 필드 추가만 보고 버전 변경을 역으로 단정하지 않는다.

### T13. 읽을 수 있는 링크 이름과 실제 읽기 권한

- **[추론·합성 입력]** “외부 협력사에 보낼 메일을 다듬어 줘. ‘여기 보세요: [검토 문서 링크]’라고 썼어. 링크는 Google Drive 문서이고 접근은 ‘제한됨’이야. 나는 열리지만 협력사 계정 권한은 아직 확인하지 못했어. 파일명은 ‘9월 정산 검토표’야. 상대가 바로 볼 수 있다고 확답하지 말아 줘.”
- 근거: S10 설명적인 링크 문구, S11 제한됨·외부 공유 제한.
- 예상 편집 실패: ‘누구나 열람 가능합니다’로 매끄럽게 포장함. 접근하지 못한 문서 내용을 요약해 넣거나 임의 공개를 해결책으로 확정함.
- **관찰 가능한 합격:** 링크 목적을 ‘9월 정산 검토표’처럼 알 수 있게 쓰고 미확인 접근 권한을 보존한다. 실제로 읽었다고 주장하거나 검토표 내용을 만들어내지 않는다. 자동으로 공개 권한 변경·메일 발송을 하지 않는다.
- 정당한 예외: 이메일 시스템이 링크 이름을 지원하지 않으면 설명과 원시 URL을 함께 쓸 수 있다. 받는 사람의 권한이 이미 확인된 입력에서는 열람 가능하다고 안내할 수 있다. 합성 링크는 실제 URL로 가장하지 않는다.

### T14. 테스트 URL 생성과 실제 업무 증빙 발급

- **[추론·합성 입력]** “QA 완료 보고 문장을 다듬고 의미도 확인해 줘. 토스 테스트 환경에서 현금영수증 `receiptUrl`이 생성되는 것까지 확인했어. 문서상 테스트 URL에는 실제 데이터가 제공되지 않아. 초안: ‘고객에게 제출할 현금영수증 발급과 조회 검증을 완료했습니다.’”
- 근거: S1 `cashReceipt.receiptUrl`, `cashReceipts.receiptUrl`.
- 예상 편집 실패: URL이 있다는 사실을 실제 발급·실데이터 조회 성공으로 바꿈. 링크가 안 보인다는 이유로 곧바로 결제 실패라고 판정함.
- **관찰 가능한 합격:** 테스트 URL 생성 확인까지만 완료로 쓴다. 실제 발급·고객 제출 가능 증빙·실데이터 조회를 검증했다고 하지 않는다. 테스트 환경의 제약을 남긴다.
- 정당한 예외: 라이브에서 실제 발급 결과와 조회 내용까지 확인한 입력에서는 그 검증 범위를 명시할 수 있다. URL 문자열을 모든 문서에 반드시 노출할 필요는 없다.

## 3. 평가 운영 시 주의

1. **언어를 개선하면서 계약을 보존하는 능력**을 본다. 코드·상태명만 반복하고 한국어 문장이 전혀 개선되지 않는 응답을 자동으로 높은 점수로 볼 이유는 없다.
2. 기술자용·고객용 입력을 짝으로 두면 과잉 토큰 유지와 과잉 번역을 함께 점검할 수 있다. 고객용에는 쉽고 짧은 설명이 정당하다.
3. 같은 주제를 ‘아직 확인 전’과 ‘확인 완료’로 바꾼 대비 입력으로 평가하면, 어떤 상황에서도 유보 문구만 덧붙이는 실패를 확인할 수 있다.
4. 원문 숫자·범위·조건이 서로 충돌하면 임의로 하나를 선택해 사실로 굳히지 않는지 본다. 불일치 지적과 입력으로 검증 가능한 교정은 허용한다.
5. 위 출처는 평가 내용의 타당성을 뒷받침할 뿐 도구 성능의 증거는 아니다. 실제 실행과 채점은 별도 작업이다.

## 4. 접근 실패와 증거 한계

- `https://style.ons.gov.uk/category/writing-about-statistics/`는 read 도구에서 `application/octet-stream`과 빈 본문만 반환했다. 읽은 근거로 사용하지 않았다. 퍼센트 관련 근거는 직접 읽힌 Eurostat로 대체했다.
- `https://developers.google.com/style/deprecation`은 HTTP 404였다. 그 URL의 내용을 추정하지 않았다. 실제로 읽힌 Google Cloud 제품 출시 단계의 한·영 본문으로 대체했다.
- 통계청 대상 검색과 ONS 대상 검색에서 web_search가 검색 결과 대신 일반 대화형 답변을 반환했다. 검색 결과가 없는 상태로 통계청·ONS 문서를 읽었다고 주장하지 않았다. 이 도구 이상은 보고했다.
- 토스·Google의 긴 페이지는 위에 명시한 관련 절만 사용했다. 뒤쪽의 미열람 절을 인용하지 않았다.
- Google 도움말에 로그인 안내가 있지만 사용한 공개 절은 읽혔다. 실제 Google Drive 개인 문서·계정·권한·파일 내용에는 접근하지 않았고 접근 가능하다고 주장하지 않는다.
- 이 연구에서는 코드 수정, API 호출, 결제, 실제 재시도, 공유 권한 변경, 메일 발송, 검증 명령을 실행하지 않았다. 근거 확인은 공개 1차 문서의 실제 본문 열람으로 수행했다.
