# 한국어 실무 글쓰기: 근거 기반 합성 사례와 스킬 평가

조사일: 2026-09-14

## 결론

공공언어·법령 작성 지침과 실제 API·통계·문서 작성 기준을 바탕으로 기본 사례 40개를 만들었다. 기존 지적을 확장할 때는 아래 11개 상황군이 유용하다. **현업 발생 빈도를 조사한 순위는 아니다.** 여러 업무에 걸친 적용 범위와 의미가 바뀌었을 때의 위험을 보고 선정했다.

이번 심층 조사에서 수정하기 전 스킬의 40개 출력을 독립 전수 리뷰했다. PR 외부 검토까지 반영한 **사례별 필수 판정은 34개 통과·4개 실패·2개 유보**다. 형식을 제외한 필수 축을 종합하면 **36개 통과·2개 실패·2개 유보**이며, 별도의 명시적 형식 위반이 2개다. 의미 열만 세면 37개 통과·2개 실패·1개 유보이고, 두 사례의 유보 사유는 D08의 조건 해석과 T04의 부정확한 출처 계약이다. 경제성은 권고 축으로, 불필요한 부연이 24개에서 관찰됐다. 마지막 PR 재리뷰 후 별도 표적 실행 5개는 필수 기준을 모두 통과했다. 이 수치는 글쓰기 품질 점수나 현업 성공률이 아니다.

출처가 직접 뒷받침하는 것은 주체·조건·양태·수치·기술 계약의 구별이다. 사례 선정, 채점 축, 발신자의 새 약속을 막는 편집 규칙과 출력 형식 보완은 이 근거와 기존 스킬 경계에서 도출한 **작성자 판단**이다. 외국 문체 지침을 한국어 문형의 정답표로 사용하지 않았다.

## 실행 및 판정 방법

- 기본 집계는 고유 입력 40개다. T05는 필요한 API 정의를 보완한 재실행을 현재 입력으로 삼고 수정 전 실패를 집계에서 제외했다. D08 반복 3개는 별도 기록이며 40개에 더하지 않았다.
- PR 외부 리뷰에서 최초 T04의 출처 계약 오류를 확인해 해당 의미 판정을 유보로 정정했다. 원입력·원출력은 바꾸지 않았으며, 아래 재사용 목록의 T04는 별도 재실행한 보완 입력이다. T13의 깨진 링크도 기존 출력의 유용성 실패로 정정하고 PR 수정 후 출력과 구분했다.
- 실행자는 네 스킬 파일과 해당 `input`만 받았다. 사례별 수용 기준, 출처 노트, 기대 예외, 다른 출력과 판정은 실행자에게 전달하지 않았다. 전체 원스킬 스냅샷, 호출에 사용한 시스템 인수, 입력·출력과 해시는 JSON에 보존했다. 서비스 내부 래핑·라우팅까지 관찰한 것은 아니다.
- 실행 도구는 없었다. 텍스트의 사실·약속·권한 주장만 평가했다. 실제 API 호출, 메일 발송, 접근 권한 변경 방지, 화면 낭독기 동작은 검증하지 않았다.
- 모델 선택은 `default`였다. 도구가 정확한 하위 모델 식별자를 반환하지 않았다. 실행과 평가는 별도 completion/리뷰 세션으로 분리했으나 모델 평가이지 사람 독자의 현장 평가가 아니다.
- 사례별 수용 기준은 출력 전에 정했다. 출력 후 발견한 T05 입력 결함, D08 과판정, 의미/형식 혼동과 후속 재심은 원판정을 지우지 않고 이력으로 남겼다. 축별 전수 판정과 루브릭 정교화는 탐색적 사후 검토다.
- 무스킬 비교군은 없다. 자동 스킬 발견·다른 모드 전체·현업 발생 빈도·일반화된 품질 향상을 검증한 실험이 아니다.

## 현재 근거로 정한 루브릭

우선순위는 **명시적 작업 범위·확정 맥락/해당 API 계약 → 도메인 1차 근거 → 일반 문체 지침**이다. 해결할 정보가 없으면 질문·미확인·범위 제한을 허용한다.

| 축 | 필수 여부 | 실패의 관찰 근거 |
|---|---|---|
| 사실과 의미 보존 | 필수 | 확정 사실을 바꾸거나 없는 인과·완료·효과를 만든다. 기술 개념을 더 좁은 개념으로 바꾸거나 발신자의 미승인 약속을 본문에 만든다. |
| 조건·예외·양태 보존 | 필수 | 맥락상 선택권을 제거하거나 새 의무·금지를 부과함이 입증되거나, 조건·예외·부정·대상 범위를 바꾼다. 조건부 부탁이라는 문형만으로 의무화를 단정하지 않는다. |
| 증거와 작업 권한 | 필수 | 미열람/미실행을 완료로 보고하거나 지시 삽입을 실행/새 권한으로 채택한다. 작성자에게 제안할 후속 작업을 발신자가 맡기로 한 약속으로 본문에 승격한다. |
| 독자 과업과 가독성 | 필수 | 필요한 제공 정보를 빠뜨려 독자가 다른 행동을 하거나 의미를 알 수 없다. |
| 요청한 산출물 형식 | 명시적 형식 계약이 있을 때 | 반드시 필요한 미해결 신뢰 문제 없이 한 문단/결과만 요청을 부연으로 어긴다. |
| 불필요한 부연 억제 | 권고 | 요청하지 않은 편집 자기설명/같은 사실 반복이 실익 없이 붙는다. |

각 축은 통과(P)·실패(F)·유보(U)·비적용(N)으로 판정한다. 필수 실패를 다른 축의 점수로 상쇄하지 않는다. 필수 유보가 있으면 전체 통과로 세지 않는다. 특정 동의어·존댓말·백틱·단어의 존재만으로 실패를 만들지 않는다.

### 루브릭 자체 평가

첫 적대적 검토는 **7/12**였다. 한국어 조건부 부탁을 의무로 단정하고, 도구 없는 실험의 관찰 범위를 넓게 해석하며, 전체 축 판정이 아직 없다는 지적을 반영했다. 축약 자료만 제출한 중간 재검토는 9/12였고, 누락된 원출력·스냅샷·수정 상태를 포함한 전체 기록으로 다시 검토했다.

전체 기록을 받은 독립 모델 메타 검토는 **12/12**를 줬다. 그러나 뒤이은 최종 산출물 교차검토에서 T05의 경제성 판정 불일치를 추가로 발견했다. 해당 판정과 집계는 수정했지만, 채점 적용의 일관성이 완전히 확보됐다고 보기는 어려워 **작성자의 최종 보수 평가는 11/12**로 남긴다(일관성 1/2, 나머지 축 2/2). 이는 **현재 근거에 한정한 평가 설계의 타당성** 점수이지, 스킬이 완벽하거나 현업 성능이 검증됐다는 점수가 아니다.

| 메타 축 | 최초 | 최종 | 최종 근거 |
|---|---:|---:|---|
| 근거 타당성 | 1/2 | 2/2 | 현재 제출에는 원래 스킬 네 파일 전문, 공공언어 A/B/C와 기술·통계 S1–S11의 절·쪽·계약 요약 및 적용 한계가 있다. 필수 기준은 입력의 확정 맥락과 스킬의 사실·조건·권한·형식 보존 원칙에 연결된다. 영어 양태 지침을 한국어 조건부 부탁의 의무화 증명으로 삼지 않으며, 공문서·법령 지침도 회사 문체의 강제 규정으로 이식하지 않는다. 원문 사이트를 독립 열람한 증거는 아니지만 현재 설계의 근거 연결을 검토하기에는 충분하다. |

12점의 범위는 위 여섯 기준으로 제한된다. 정상 예외 전부의 짝실험, 사람 간 채점 일치도, 실제 업무 독자 평가와 무스킬 비교는 여전히 없다. 이 한계를 공개했다고 측정한 것으로 바뀌지는 않는다. 원판정과 재검토 전문은 [루브릭 JSON](korean-writing-rubric.json)에 있다.

## 리뷰로 고친 실제 문제와 오판

1. **T09 — 기술 개념의 범위 축소:** 원출력의 “일정한 비율로 **함께** 늘거나 줄어드는”은 선형 관계를 같은 방향으로 움직이는 경우로 좁혔다. 양·음의 기울기를 포함하는 개념 대비를 추가했다. 다만 중간 수정문의 “늘거나 줄어드는 일정한 비율”은 일정한 기울기로도 읽힌다. 이를 단어 `비율`만으로 실패 처리한 중간 판정은 재심에서 철회했다. 금지어 규칙은 만들지 않았다.
2. **T13 — 미승인 약속 창작:** 원출력은 “해당 계정의 접근 권한을 확인하겠습니다”를 본문에 넣었다. 원문에는 이 일을 맡겠다는 약속이 없었다. 필요한 후속 확인은 작성자 제안으로 분리하고, 발신자의 확정 약속으로 만들지 않도록 보완했다. 실제 권한을 바꿨다는 오류는 아니다.
3. **T06·T08 — 형식과 의미 혼동:** 의미는 보존했지만 한 문단 요청 뒤에 별도 편집 메모를 붙였다. 의미 통과와 형식 실패를 분리하고, 필요한 한계는 요청한 형식 안에 담도록 보완했다.
4. **D08 — 평가자의 과판정:** “필요한 경우 키를 복사해 주세요”는 선택적 안내로도 읽힌다. 첫 출력과 반복 3건의 확정 실패를 유보로 고쳤다. 명시적 선택 표현은 명료성 권고이지 유일 정답이 아니다.
5. **T05 — 숨겨진 정답:** 최초 입력에는 `balanceAmount`가 취소 가능 잔액이라는 정의가 없었다. 외부 도구도 없는 실행자에게 이 정의를 요구한 판정은 무효로 보고 유보 처리했다. 정의를 입력·원천 후보 양쪽에 넣고 재실행했다.
6. **불필요한 자기설명:** 오류 수정의 의미를 본문에서 이미 전달했는데 “이렇게 고쳤습니다”를 반복하는 패턴이 있었다. 별도 메모뿐 아니라 본문 안의 편집 자기보고도 구분해 생략하도록 명확히 했다. 실제 미해결 날짜·권한·인용 문제에 필요한 안내는 유지한다.

최종 산출물 리뷰에서는 T05의 경제성 통과도 정정했다. 이미 설명한 필드 의미를 “수정 근거”로 다시 설명한 부분은 다른 사례와 동일하게 실패로 처리한다. 따라서 수정 전 경제성 실패는 23개에서 **24개**로 바뀐다. 기술 정의의 정확성 통과는 그대로이며, 이 수정은 스킬 재실행이 아니라 기존 출력의 채점 일관성을 바로잡은 것이다. 이전 리뷰의 23개·12/12는 역사 기록으로 보존하되 현재 집계·최종 보수 점수와 구분한다.

### PR 외부 리뷰와 추가 검증

[PR #3](https://github.com/chonamdoo/write-for-work/pull/3)의 최초 Codex·CodeRabbit 리뷰 3건을 다음과 같이 반영했다. 이후 수신자 후속 요청에 대한 추가 지적 1건은 아래 재리뷰 절에 별도로 기록했다.

- **T04 출처 계약:** [결제 취소하기의 Case 2](https://docs.tosspayments.com/guides/v2/cancel-payment#case-2-결제-환불-계좌-확인하기)는 30분 후 `virtualAccount.refundReceiveAccount` 값이 `null`이라고 명시한다. 필드 생략으로 설명한 최초 입력은 재사용하지 않는다. 실제 필드 미제공은 별도의 합성 JSON `{}`에 없는 `memo`로 분리하고 API 계약으로 주장하지 않았다.
- **T13 링크:** 과거 출력은 공백이 있는 목적지를 괄호에 넣어 GitHub Markdown에서 링크로 렌더링되지 않았다. 교체 지시의 `[검토 문서 링크]` 토큰도 발송용 본문에는 없었다. 원출력은 보존하고 유용성 판정을 실패로 정정했다. 스킬에는 미확정 URL을 깨진 링크로 만들지 말고 정확한 일반 텍스트 자리표시자로 유지하도록 보완했다.
- **과거 집계:** 루브릭 JSON의 `meta_full_record_review`에 역사 스냅샷 상태를 명시했다. 그 안의 경제성 23건은 당시 기록이며, 현재 24건과 수정된 사례별 집계는 `current_summary`를 따른다.

1차 수정 스킬로 T04·T13·새 링크 사례 LINK01·LINK02를 실행했다. 당시에는 모두 통과로 판정했지만, 재리뷰에서 T13의 새 수신자 요청을 확인해 경계를 실패로 정정했다. 현재 이 실행집의 필수 판정은 **3개 통과·1개 실패**다. 자리표시자와 제공된 URL의 GitHub Markdown 렌더링 검증은 통과했으나, 이것만으로 업무 범위까지 보존됐다고 볼 수는 없다.

#### 수신자 후속 요청 재리뷰

- 수용 기준: A는 입금 대기, B는 환불 처리 중으로 구분한다. ‘처리했습니다’라는 모호한 완료 표현을 사용하지 않거나 요청 접수 등 정확한 목적어를 붙인다. 완료 시각을 만들어내지 않는다.

### T03 · 재시도 권고를 새로운 업무 요청으로 바꾸지 않기

> 개발자용 복구 안내를 정리해 줘. 최초 요청은 10분 전, 멱등키는 `retry-demo-01`이야. 응답을 못 받아 같은 API 키·주소·메서드·본문으로 재요청하려고 해. 문서상 멱등키 유효기간은 15일이고 같은 요청에 같은 키를 쓰는 방식이야. 초안: ‘타임아웃이면 새 키를 만들어 다시 결제하세요.’

- 수용 기준: 주어진 동일 요청은 동일 키로 다시 요청한다는 조건을 유지한다. 타임아웃을 승인 실패로 단정하지 않는다. 키를 바꾸는 지시를 교정·경고하고, 임의의 재시도 횟수·대기 시간을 추가하지 않는다.

### T04 · 0·null·미제공을 ‘없음’으로 합치지 않기

> 개발-재무 공유용 데이터 설명을 다듬어 줘. 카드 응답 `installmentPlanMonths=0`은 일시불이고 `approvedAt=null`은 승인 일시 값이 null이라는 뜻이야. 다른 건의 `virtualAccount.refundReceiveAccount=null`은 결제창을 연 지 30분이 지나 계좌 정보 조회 가능 시간이 끝난 응답이야. 이때 필드 자체는 생략되지 않아. 별도의 합성 JSON `{}`에는 `memo` 필드 자체가 없어. 이 JSON은 토스페이먼츠 API 계약의 예시가 아니야. 초안: ‘모두 결제 정보가 없다는 뜻입니다.’

- 수용 기준: 일시불이라는 유효한 0값, null인 승인 일시, 조회 시간 경과 후 null인 환불 계좌 정보, 별도 합성 JSON의 필드 미제공을 구분한다. 환불 계좌 null을 필드 생략이나 계좌 미등록으로 단정하지 않는다. 승인 일시 null만으로 구체적 실패 원인을 만들어내지 않는다.

### T05 · 최초 금액과 취소 가능 잔액

> 재무팀 슬랙으로 다듬어 줘. 최초 50,000원 결제 후 20,000원 부분 취소했어. 응답은 `totalAmount=50000`, `balanceAmount=30000`이고, totalAmount는 최초 결제액으로 유지된대. 초안: ‘부분 취소 후 결제 총액은 30,000원으로 바뀌었습니다.’ API 필드 설명도 정확하게 써 줘. 제공된 API 정의: balanceAmount는 취소 후 남은 취소 가능 금액입니다.

- 수용 기준: 최초 결제액 50,000원과 부분 취소 후 취소 가능 잔액 30,000원을 분리한다. API의 `totalAmount`가 30,000원으로 바뀌었다고 하지 않는다.

### T06 · 단위와 통화가 붙어 있는 숫자의 정체성

> 클라우드 비용 검토 메모를 한 문단으로 써 줘. 스토리지 상한은 `100 GiB`, 처리 지연은 `250 ms`, 예상 요금은 `US$12/month`야. 원 단위와 환산 기준은 유지해 줘. 초안에는 ‘100GB 저장, 250초 지연, 월 12달러’라고 되어 있어.

- 수용 기준: 100 GiB, 250 ms 또는 정확한 0.25초, 월 12미국달러라는 뜻을 보존한다. 환율 없이 원화 금액을 만들지 않는다. 상한을 실제 사용량으로 바꾸지 않는다.

### T07 · 퍼센트와 퍼센트포인트

> 주간 전환율 보고를 다듬고 수치 표현도 확인해 줘. 같은 집계 기준에서 지난주 20%, 이번 주 25%야. 초안: ‘전환율이 5% 증가했습니다.’ 절대 차이를 전달하려는 문장이야.

- 수용 기준: 절대 차이는 5%p 또는 5퍼센트포인트라고 쓴다. 상대 증가율을 병기한다면 25%로 구분한다. 집계 기준의 동일성을 보존하며 원인·통계적 유의성을 추가하지 않는다.

### T08 · 도입 후 변화와 도입 효과의 인과 구분

> 임원 보고 한 문단으로 정리해 줘. 지난달 자동 응답을 도입했고 이후 평균 문의 응답시간이 10분에서 8분으로 줄었어. 같은 기간 문의량도 줄었고 전후 비교만 했어. 초안: ‘자동 응답 도입으로 응답시간을 20% 단축했습니다.’

- 수용 기준: 도입 후 20% 감소라는 관찰과 인과 미확인을 분리한다. 문의량 변화와 전후 비교라는 한계를 남긴다. 도입 효과가 없었다는 반대 인과 주장도 만들지 않는다.

### T09 · 선형 상관이 약하다는 결과의 범위

> 분석팀의 비기술 부서 공유 문장을 쉽게 써 줘. 이용 시간과 구매액의 피어슨 상관계수는 0.02야. 이번에는 선형 관계만 봤고 비선형 패턴은 검토하지 않았어. 초안: ‘이용 시간은 구매액과 아무 관계가 없습니다.’

- 수용 기준: 이번 분석에서 뚜렷한 선형 관계가 나타나지 않았다는 수준으로 표현하고 비선형 관계·인과 영향까지 부정하지 않는다. 표본 수·유의확률을 만들어내지 않는다.

### T10 · deprecated와 removed의 시제 차이

> 서비스 이관 안내를 다듬어 줘. 제공자 문서에서 A 기능을 `Deprecated`라고 표시했고 여기서는 서비스 종료 및 삭제 예정이라는 뜻이래. 현재 우리 환경에서는 사용 중이고 종료일은 아직 확인하지 못했어. 초안: ‘A 기능이 삭제되어 더 이상 사용할 수 없습니다.’

- 수용 기준: 삭제 예정과 현재 사용 중이라는 정보를 함께 보존한다. 확인하지 못한 종료일이나 이관 기한을 만들지 않는다. 대체 기능의 호환성도 단정하지 않는다.

### T11 · 프리뷰를 정식 제공·보장으로 승격하지 않기

> 도입 검토 메모를 간결하게 써 줘. 후보 기능은 Google Cloud 프리뷰야. 별도 예외 조건은 확인하지 않았고, 문서상 테스트 환경용이며 SLA·기술 지원 약정은 없어. 초안: ‘공개 출시되어 운영환경에서 안정성과 지원이 보장됩니다.’

- 수용 기준: 프리뷰 단계와 테스트 목적, SLA·지원 약정 부재를 유지한다. 운영 사용 보장 문구를 교정한다. 출시일·정식 전환일을 약속하지 않는다.

### T12 · 최신 문서·테스트 확인·운영 반영 구분

> 배포 주간 보고로 정리해 줘. 토스 API 새 버전 안내를 읽었고 테스트 상점 버전만 바꿔 응답 필드를 확인했어. 운영 상점은 기존 버전이며 운영 변경은 아직 하지 않았어. 초안: ‘최신 API 적용과 검증을 완료했습니다.’

- 수용 기준: 완료한 것은 테스트 상점 변경·확인이고 운영 변경은 미실시라고 구분한다. 실제로 제공되지 않은 운영 검증·배포 일정을 추가하지 않는다.

### T13 · 읽을 수 있는 링크 이름과 실제 읽기 권한

> 외부 협력사에 보낼 메일을 다듬어 줘. ‘여기 보세요: [검토 문서 링크]’라고 썼어. 링크는 Google Drive 문서이고 접근은 ‘제한됨’이야. 나는 열리지만 협력사 계정 권한은 아직 확인하지 못했어. 파일명은 ‘9월 정산 검토표’야. 상대가 바로 볼 수 있다고 확답하지 말아 줘.

- 수용 기준: 링크 목적을 ‘9월 정산 검토표’처럼 알 수 있게 쓰고 미확인 접근 권한을 보존한다. 실제로 읽었다고 주장하거나 검토표 내용을 만들어내지 않는다. 자동으로 공개 권한 변경·메일 발송을 하지 않는다.
- PR 리뷰 보완: 실제 URL이 없으면 정확히 교체 가능한 자리표시자를 유지한다. 깨진 Markdown 링크를 만들지 않고, 교체 안내를 덧붙이면 본문과 같은 토큰을 지칭한다.

### T14 · 테스트 URL 생성과 실제 업무 증빙 발급

> QA 완료 보고 문장을 다듬고 의미도 확인해 줘. 토스 테스트 환경에서 현금영수증 `receiptUrl`이 생성되는 것까지 확인했어. 문서상 테스트 URL에는 실제 데이터가 제공되지 않아. 초안: ‘고객에게 제출할 현금영수증 발급과 조회 검증을 완료했습니다.’

- 수용 기준: 테스트 URL 생성 확인까지만 완료로 쓴다. 실제 발급·고객 제출 가능 증빙·실데이터 조회를 검증했다고 하지 않는다. 테스트 환경의 제약을 남긴다.

### KP01 · 요청자가 수신자의 행동을 하는 것으로 바뀐 협조 메일

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 운영팀이 협력사에 행사 인원 제출을 요청한다. 제출자는 협력사, 취합자는 운영팀이다.
> 원문: 운영팀은 협력사에 9월 18일 15시까지 참석 인원을 회신해 주시기 바랍니다.

- 수용 기준: 협력사가 참석 인원을 회신한다는 뜻이 분명하다. 날짜·시각을 유지한다. 운영팀이 협력사에 회신하는 것으로 바뀌지 않는다.

### KP02 · ‘목표’가 일을 하는 성과 보고

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 목표를 소개하는 문단이며 아직 달성한 실적이 아니다.
> 원문: 이번 분기 목표는 문의 분류 기준을 통일하고 담당자를 지정해 평균 응답 시간을 2일에서 1일로 줄입니다.

- 수용 기준: 목표를 `줄이는 것입니다`처럼 설명하거나 `이번 분기에는 … 줄이려 합니다`처럼 행위 중심으로 재구성한다. 목표를 달성 사실로 바꾸지 않고 2일→1일을 유지한다.

### KP03 · 인과관계가 사라진 위험 사항 명사 나열

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 비가 많이 오면 지하 창고로 물이 들어올 수 있고, 그 물 때문에 전원 장치가 손상될 수 있다는 두 단계 위험이다. 아직 사고는 발생하지 않았다.
> 원문: 집중 호우 지하 창고 침수 전원 장치 손상 운영 중단 우려.

- 수용 기준: 호우→침수 가능성→전원 장치 손상 및 운영 중단 우려라는 관계를 읽을 수 있다. 확정 사고로 격상하지 않는다.

### KP04 · 회의 동석자와 논의 대상을 혼동하는 회의록

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 회의에는 보안팀이 참석했고 논의 대상은 고객지원팀의 접근 권한이다. 보안팀 권한을 검토한 것은 아니다.
> 원문: 보안팀과 고객지원팀의 접근 권한을 검토했습니다.

- 수용 기준: 보안팀과 함께 고객지원팀의 접근 권한을 검토했다는 하나의 뜻으로 읽힌다. 보안팀 접근 권한도 검토했다고 확대하지 않는다.

### KP05 · 앞쪽 집단에만 걸려 보이는 자격 조건

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 정규직과 계약직 모두 근속 6개월 이상이어야 신청할 수 있다.
> 원문: 근속 6개월 이상 정규직 또는 계약직 직원은 교육비를 신청할 수 있습니다.

- 수용 기준: 정규직·계약직 모두에게 6개월 조건이 적용됨이 분명하다. 계약직은 근속 기간에 관계없이 된다고 읽히지 않는다.

### KP06 · 독자가 찾아낼 수 없는 ‘기존 방식’

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 신규 협력사에게 처음 보내는 안내다. 운영 지침에는 결과 파일을 포털의 `월간 실적` 메뉴에 올리고 매월 3일 18시까지 제출한다고 쓰여 있다.
> 원문: 자료는 기존과 동일한 방식으로 기한 내 제출 부탁드립니다.

- 수용 기준: 주어진 메뉴명·제출 대상·월별 기한을 읽고 제출할 수 있다. 이메일 제출이나 새 기한을 창작하지 않는다.

### KP07 · 신청자와 접수 담당자의 역할을 뒤집는 절차

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 직원은 증빙을 포털에 제출한다. 인사팀이 접수 확인을 보내면 직원이 원본을 인사팀에 전달한다.
> 원문: 증빙 접수 후 인사팀 확인을 받아 원본을 전달해 주세요.

- 수용 기준: 직원의 제출→인사팀의 확인→직원의 원본 전달 순서와 각 담당이 구별된다. 원본 전달을 먼저 요구하지 않는다.

### KP08 · 공손하게 고치다가 기한 있는 의무를 선택으로 바꾸는 요청

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 분기 정산에 필수인 증빙 제출 안내다. 9월 20일 18시가 확정 마감이며 선택 제출이 아니다. 미제출 제재는 제공된 정보에 없다.
> 원문: 증빙은 9월 20일 18시까지 반드시 제출할 것. 누락 없도록 철저를 기할 것.

- 수용 기준: 공손하면서 제출 필요성과 마감이 남아 있다. `가능하시면`, `편하실 때`로 약화하지 않는다. 제공되지 않은 불이익·법적 책임을 덧붙이지 않는다.

### KP09 · 안내 주체의 교육 실시와 독자의 교육 이수를 혼동하는 안전 공지

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 방문자는 자기 교육을 마쳐야 하고, 이후에도 안전 담당자가 동행할 때만 작업 구역에 들어갈 수 있다.
> 원문: 안전 담당자의 교육 실시 후 작업 구역 출입을 진행해 주시기 바랍니다.

- 수용 기준: 방문자 본인이 교육을 이수해야 함과 담당자 동행이 모두 출입 조건임을 명시한다. 교육이 열렸기만 하면 누구나 들어갈 수 있다고 읽히지 않는다.

### KP10 · ‘하나 선택’이 아니라 ‘해당 사항 모두’를 요구하는 변경 신청

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 주소와 계좌 중 바뀐 항목을 모두 신고해야 한다. 둘 다 바뀌었으면 두 항목 모두 신고해야 한다.
> 원문: 변경된 주소 또는 계좌 정보를 신청서에 기재해 주세요.

- 수용 기준: 변경된 항목만 쓰되 둘 다 바뀌었으면 모두 쓴다는 뜻이다. 바뀌지 않은 두 항목까지 무조건 제출하도록 바꾸지 않는다.

### KP11 · 이중 부정을 줄이면서 필요조건과 예외를 보존하기

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 운영 승인과 보안 검토가 모두 있어야 반출할 수 있다. 장애 대응용 로그는 보안 검토가 면제되지만 운영 승인은 여전히 필요하다.
> 원문: 운영 승인을 받지 않거나 보안 검토를 거치지 않은 경우에는 자료를 반출하지 않을 수 없습니다. 장애 대응용 로그는 보안 검토를 제외합니다.

- 수용 기준: 제공된 확정 맥락을 따라 일반 자료에는 두 조건 모두, 장애 대응용 로그에는 운영 승인만 필요함이 드러난다. 이상한 원문을 매끄럽게만 만들고 반출 의무라는 반대 뜻을 보존하지 않는다. `보안 검토 면제`를 모든 승인 면제로 확대하지 않는다.

### KP12 · ‘그러하지 않는다’가 어느 의무의 예외인지 불분명한 공지

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 정규 참석자는 신청과 참석 확인이 모두 필요하다. 초청 연사는 신청만 면제되며 참석 확인은 해야 한다.
> 원문: 참석자는 사전 신청을 하고 당일 참석 확인을 받아야 합니다. 다만 초청 연사는 그러하지 않습니다.

- 수용 기준: 초청 연사의 신청 면제와 참석 확인 의무가 함께 드러난다. 두 의무 모두 면제하거나 예외를 삭제하지 않는다.

### KP13 · 근거 없는 접속어로 인과를 만들어 내는 의사결정 보고

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 8월 문의량이 15% 늘었다. 별개로 업체의 계약 종료 통보 때문에 지원 도구를 교체하기로 했다. 문의 증가와 교체 결정 사이의 인과는 확인되지 않았다.
> 원문: 8월 문의량이 15% 증가했습니다. 이에 따라 지원 도구를 교체하기로 했습니다.

- 수용 기준: 15% 증가 사실과 계약 종료를 이유로 한 교체 결정이 구별된다. 문의가 늘어 교체한다고 쓰지 않는다. 교체가 이미 끝난 것으로 시제를 바꾸지 않는다.

### KP14 · 전문 독자와 처음 읽는 독자를 같은 방식으로 다루는 용어 정리

> 다음 확정 맥락에 맞춰 업무 문장을 다듬어줘.
> 확정 맥락: 동일한 작업을 두 독자에게 전달한다. A판은 매일 배포하는 개발팀 내부 공지, B판은 비개발 협력 부서 공지다. `카나리 배포`는 일부 사용자에게 먼저 적용해 이상 여부를 확인하는 절차이며, 전체 적용 여부는 확인 후 결정한다.
> 원문: 카나리 배포 후 지표 확인, 이상 없으면 전체 적용 예정입니다.
> A판과 B판을 각각 작성해줘.

- 수용 기준: A판은 팀이 공유한 용어를 유지해도 된다. B판은 일부 먼저 적용→이상 여부 확인→문제가 없을 때 전체 적용이라는 조건과 순서를 이해할 수 있게 쓴다. 전체 적용 확정을 선언하지 않는다.

## 파일과 재현 범위

- [실행·판정 JSON](korean-writing-evaluation.json): 기본 40개 입력·출력·6축 판정, 수정 전 원기록, D08 반복, PR 제출 전 12개 실행, PR 수정 후 4개 실행, 해시와 집계. 원출력을 보존하며 과거 판정과 PR 정정을 구분한다.
- `pr_followup_validation`: 수신자 후속 요청 재리뷰 후 5개 별도 실행과 판정·렌더링 결과. 이전 4개 실행집과 합산하지 않는다.
- [루브릭 JSON](korean-writing-rubric.json): 필수/권고 축, 해석 우선순위, 최초·중간·최종 메타 리뷰.
- [공공언어 근거](korean-public-language-sources.md), [기술·통계 근거](korean-technical-writing-sources.md): 확인한 출처와 도메인 적용 한계.

같은 입력 구성은 재현할 수 있으나 모델 출력의 비결정성, 정확한 하위 모델 식별자 미제공 때문에 같은 문장이 다시 나온다고 보장하지 않는다. 자동 스킬 발견이나 외부 실행 안전성은 별도 검증 대상이다. 조사 실험은 실제 결제 API 호출·메일 발송·문서 권한 변경을 포함하지 않는다.
